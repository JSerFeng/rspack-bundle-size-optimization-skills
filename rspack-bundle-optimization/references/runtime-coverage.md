# Runtime Loading and Execution Coverage

Use runtime coverage when the question concerns which JavaScript a page or
interaction requests, or which parts of the loaded JavaScript execute.

Rspack commonly emits modules inside generated wrappers, called module
factories in the tool output and filenames below. Concatenated inner modules
may share one wrapper.

A V8 range with `count === 0` means only “not observed during this capture.”
It does not prove that code is unused, unwanted, removable, side-effect free,
or safe to defer. Confirm those decisions from the loading cause, source,
product behavior, and production output.

## Use the correct build

- Use `production-debug` to map Rspack chunks and generated module wrappers. Its
  generated bytes are only for locating code.
- Use `production` to confirm byte and request changes. Measure a specific
  product or performance metric separately before claiming a user-facing
  improvement.
- Use `development` only to debug the app or check tool support. Do not report
  its bytes or coverage as production evidence.

Keep entries, compilation targets, feature flags, splitChunks, dependencies,
runtime, and plugins unchanged between `production` and `production-debug`,
apart from the debug settings defined in `SKILL.md`.

In this document, `compilation target` means the configured JavaScript or
browser compatibility target. `runtime target` means a page, iframe, worker,
or service worker observed through Chrome. Keep compilation targets unchanged.

## Capture through Chrome

Prefer the official Chrome DevTools MCP server when it can:

- start and stop precise JavaScript coverage;
- return exact script source;
- show loaded resources or network requests;
- discover and attach to page, iframe, dedicated-worker, shared-worker, and
  service-worker targets.

Before capture, inspect the tools available in the current session and record
the exact coverage, source, network, and target commands used. Prefer the live
tool list over an older public reference.

For the default page pass, use function-level precise coverage with
`callCount: true` and `detailed: false`. Use block-level coverage only for a
focused follow-up.

### Fallback order

If the MCP cannot provide a required fact, record the missing command or exact
error, then use the first fallback that can support the intended conclusion:

1. raw Chrome DevTools Protocol with
   `Profiler.startPreciseCoverage`, `Profiler.takePreciseCoverage`, and
   `Debugger.getScriptSource`;
2. Puppeteer-style coverage with equivalent function ranges and exact source;
3. range-only or script-level coverage for script-level conclusions only.

To decide whether a specific generated module wrapper ran, use function ranges
and the exact script source from the same build. Without both, report only
whether the whole script ran.

### DevTools Coverage panel

Use the built-in Coverage panel only when the live MCP tool list lacks the
required coverage/source support or the MCP command fails and that error is
recorded.

For this limited fallback:

1. select `Per function`, exclude content scripts, and start before navigation
   or reload;
2. save the original JSON and its `text` before clearing the panel;
3. state that runtime target ids, worker attachment, complete function
   list, and trustworthy call counts are unavailable;
4. do not pass the export to `normalize-runtime-coverage.cjs`;
5. report observed source ranges as UTF-16 code-unit offsets, not bytes or call
   counts;
6. report generated module-wrapper ranges only when a separate extractor checks their
   boundaries against the exact exported source, and label them
   `ui-range-inference`.

For each mapped wrapper, keep its asset URL, byte range, module id when
available, observed range, source hash, and a short source excerpt.

The panel cannot support a complete conclusion for a scenario with a relevant
worker because it cannot show that worker's attachment and startup coverage.
Mark that part of the result incomplete or use a fallback that attaches to the
worker.

## Define each scenario

Name every scenario. Common examples are:

- `first-screen-cold`: cold-cache page load to a named ready condition;
- `first-screen-warm`: the same ready condition with the intended warm cache;
- `critical-interaction`: the interaction that must load deferred code.

Record:

- run id, scenario id, build mode, run number, URL, browser version, viewport,
  user state, feature flags, locale, cache setting, and service-worker setting;
- coverage start, navigation start, ready condition, fixed wait after ready,
  capture end, and interaction steps;
- expected and observed targets;
- browser errors, failed requests, and loaded JavaScript resources.

Start coverage before navigation. Prefer an application-ready marker followed
by a fixed wait instead of an open-ended `networkidle` wait.

Repeat each build mode used by the final conclusion three times. Repeat
`production-debug` when the conclusion depends on module-wrapper execution,
and repeat `production` when it depends on requests or a performance metric.
In `audit-only`, repeat only the unchanged state; in `optimize`, repeat both
unchanged and changed states. Apply the same rule to an affected critical
interaction. Keep runs separate so instability stays visible. A shorter
capture may guide the analysis but cannot support the final runtime claim.

`takePreciseCoverage` resets accumulated counters. Save each result before
taking another sample.

## Serve the production-debug build

Build `production-debug`, then use the project's production server, preview
server, or serve command. Use the ordinary development server only when no
production-like option exists, and label the result as limited.

Before capture:

- serve one fresh build rather than mixed incremental output;
- use proxying only for APIs and auth/session dependencies already required by
  the scenario;
- probe important API routes for status, content type, and response shape;
- check that SPA fallback rules do not rewrite API paths to HTML;
- record the build command, serve command, environment, URL, ready condition,
  server output, console errors, failed requests, and API responses;
- confirm that served JavaScript matches the measured build.

For the real run, start coverage first and then reload or navigate. Starting
coverage after navigation misses startup modules.

If startup or navigation fails, inspect the actual error, resolved config,
port, asset path, service worker, proxy, auth/session state, and failed
response. Retry a fresh build when served source no longer matches V8 offsets.
Fix local command mistakes, missing environment variables, or occupied ports
only when the intended scenario stays unchanged.

Ask the user before relying on a repair that changes:

- page, route, entry, deployment mode, region, account, login state, cache
  setting, or feature flags;
- API mocking, suppression, or redirection beyond the project's established
  local proxy;
- service workers, preloads, polyfills, feature rollout, analytics, auth,
  error handling, or runtime plugins;
- compilation targets, build mode, minimization, splitChunks, dependencies,
  or other production settings;
- product code or config solely to make coverage pass.

When no safe repair remains, mark the runtime conclusion incomplete and record
the command, error, attempted fix, and missing project input or approval.

If an incremental server returns changed source under an unchanged hash, stop
it, create a clean build, and capture again. Browser cache changes do not fix a
build/source mismatch.

## Include every relevant target

A page-only capture is incomplete when the scenario creates relevant iframes
or workers.

Prefer MCP target attachment before startup. If raw CDP is required:

1. enable target discovery and flattened auto-attach;
2. enable Debugger and Profiler coverage in each target before its startup code
   continues;
3. record target id and type on every script;
4. compare expected targets with targets present in the raw capture.

If a worker starts before attachment, record the missing startup window. Do
not treat the absent count as zero execution.

## Save and normalize raw data

Keep the original capture exactly as returned by Chrome or the coverage tool.
The normalizer accepts:

- a CDP `Profiler.takePreciseCoverage` result or array of script results;
- `targets[].{targetId,targetType,result}` for multiple targets;
- optional loaded-script and session JSON;
- an exact-source manifest;
- optional `compilation-data.json`.

Recommended source manifest:

```json
{
  "scripts": [
    {
      "targetId": "page-target-id",
      "scriptId": "123",
      "url": "https://example.test/static/js/page.js",
      "source": "exact source returned by Debugger.getScriptSource",
      "sha256": "..."
    }
  ]
}
```

`sourcePath` relative to the manifest may replace inline `source`.
`Debugger.getScriptSource` is preferred. HTTP retrieval is acceptable only
when the returned JavaScript exactly matches V8 length and hash; redirects,
rebuild races, source transforms, or mismatches are failures.

Normalize:

```bash
node <skill>/scripts/normalize-runtime-coverage.cjs \
  --coverage <raw-precise-coverage.json> \
  --loaded-scripts <loaded-scripts.json> \
  --session <session.json> \
  --source-manifest <script-sources.json> \
  --compilation <capture>/compilation-data.json \
  --include-url-prefix <application-origin-or-asset-prefix> \
  --out-dir <run>/runtime/<scenario>/<repetition>
```

Use `--fetch-sources` only when debugger source was not captured and the URLs
still return the identical build.

The normalizer writes:

- `runtime-coverage-session.json`;
- `runtime-coverage-scripts.jsonl`;
- `runtime-coverage-modules.jsonl`;
- `runtime-coverage-summary.json`;
- `runtime-coverage-failures.jsonl`;
- `runtime-coverage-manifest.json`.

It performs exact mapping and arithmetic only. Keep original Coverage-panel data
and any `ui-range-inference` output in a separate directory.

## How generated module-wrapper mapping works

For `production-debug` or development-style Rspack chunks, the normalizer:

1. finds the unnamed top-level V8 function spanning the complete script;
2. builds function containment;
3. considers direct children of the script root;
4. checks that source starts with the encoded function name and Rspack
   object-method syntax;
5. records the outer wrapper's execution count and generated bytes.

This prevents a nested callback from being mistaken for a separate module
wrapper. Duplicate module ids remain separate.

For a concatenated root, the result is `coarse-concatenated-factory` with its
members. Coverage cannot assign execution to individual inner modules. A
runtime-only script with no module wrappers is valid and is not a mapping
failure.

## Verify the capture

```bash
node <skill>/scripts/verify-runtime-coverage-artifacts.cjs \
  --dir <run>/runtime/<scenario>/<repetition> \
  --require-start-before-navigation \
  --require-target-types page,worker
```

Set required target types from the application. The verifier exits nonzero for
missing or inconsistent data, including:

- empty or malformed capture output;
- a loaded script missing from coverage;
- missing, changed, or mismatched source;
- an unrecognized Rspack module-wrapper boundary;
- coverage starting after navigation;
- an expected page, iframe, worker, or service-worker target missing;
- normalized files changed after their hashes were recorded.

Keep warnings and failures in the evidence. First try a fresh capture or a
narrower mapping fix. If the problem remains, state the failed attempt,
affected scope, and why the conclusion is incomplete.

## Analyze runtime results and validate any change

For each scenario, keep every valid run. Call an asset or request stable only
when it appears in every valid repetition; show all other results separately.

Identify an asset from its normalized request URL or emitted path, the compiler
that emitted it, and its saved exact source or content hash. For a comparison
in which content-hashed names change, use entry/chunk relationships to pair the
old and new assets. Do not pair assets from the filename pattern alone.

Report:

- stable requested assets with exact raw/gzip bytes and, for a comparison,
  assets removed, added, or changed;
- unstable assets separately;
- module-wrapper execution counts as supporting data, not confirmed savings;
- for a comparison, shared chunk-group assets separately from assets removed
  only by the change.

Do not claim a whole named chunk group when other roots still load its shared
assets. Confirm the actual production request and byte difference.

For each important runtime item, answer:

1. what requested the asset;
2. which entry, async boundary, chunk group, splitChunks rule, or runtime call
   caused it to load;
3. whether zero counts were stable and whether another required scenario used
   the code;
4. what the complete source and consumers do;
5. whether the product needs the feature at that point;
6. what focused source or config change, if any, can move the loading boundary
   without changing required behavior.

After a change, rebuild production, compare the same total/initial/route
scopes, repeat the same scenarios, and run the critical interaction.

For deferred loading, end or restart first-screen coverage before running the
interaction. Confirm that the assets removed from first screen load on demand,
their module wrappers execute, the expected user-visible behavior completes,
and network/console behavior remains correct.

For a worker-related change, replay worker creation, readiness or first
message, error and fallback behavior, the affected consumers, and termination
when the product normally terminates the worker.

A production byte or request difference confirms only that loading changed.
Claim faster behavior only after measuring a named performance metric under
the same cache, page, user-state, and interaction conditions.

Report each item as:

1. observed browser result;
2. loading cause;
3. relevant source and, when applicable, change;
4. why required behavior is preserved;
5. production byte/request result;
6. repeated scenario and risk checks.
