# 分析已抓取的数据

把已测量的资源统计范围转化为有因果解释、源码支撑。

使用 [measurement.md](measurement.md) 中的统计范围定义。

按项目需要编写并接入数据收集插件，见 [data-capture](data-capture.md)。
逐个执行所有在下面列出的优化检查项目，必须全部项目都执行，如果有失败则尝试修复后重试，如果仍然失败则记录失败原因：

## 检查 Chunk 是否包含非必要 Module

由 SplitChunks 的 `name` 配置或 `webpackChunkName` 注释产生的 Chunk 可能是由多个 Chunk 的 Module 聚合，这种 Chunk 可能包含有不必要的体积加载。设法访问到 Rspack 配置，给 Rspack 配置中增加一个插件访问所有的 Chunk Group 中所有的 chunks，收集到他们所有 modules。一个 Chunk Group 可能有多个 origins，每一个 origin 代表一个入口 module，如果是由 `name` 或 `webpackChunkName` 形成的 Chunk Group，他们的 origins 就可能有多个，分别分析各个 origin 所有静态依赖 module，然后看对应的 origin 造成的所有静态依赖 module，是否刚好等于该 chunk group 的所有 module，如果相等说明刚好是加载了需要的 module，反之则说明不同 origin 各有一些 unused modules 加载。

找出所有 unused modules 加载，随后分析是 splitChunks name 或 `webpackChunkName` 导致的还是其他，然后优化可以通过去掉对应的 name / `webpackChunkName` 来尝试优化的收益。

这是编译时分析；需要确认页面实际加载和执行情况时，按
[数据抓取中的浏览器运行数据说明](data-capture.md#浏览器运行数据按需) 补充验证。

## 分析 export usage

目标是解释哪些代码为何被保留、哪些引用或语法可以调整，并验证候选收益。
必须按下面的范围、台账和完成条件系统性执行；查询次数、抽样定位成功率和工具测试
不能作为完成优化分析的依据。使用 [usage graph 查询工具](usage-query.md) 按需取证，
映射细节见 [算法说明](usage-graph-source-mapping.md)。

### 1. 建立影响面清单和分析台账

先确认 compiler、构建快照和用户关心的总量/首屏/路由范围。结合产物及 chunk/module
数据列出范围内的模块实例和导出，不能只搜索熟悉的包或挑几条容易查询的链。
记录实际产物归属、体积、影响的入口/路由，以及 namespace、unknown、重复版本等信号，
据此排序。无法精确归因到导出的体积要注明使用模块/包级估算；源码大小和引用数只能
辅助排序，不能当作可节省字节数。避免重复累计共享模块或拼接模块。

若目标是 export 裁剪，将单份保留代码大小与跨 chunk 重复发射大小分开排序；后者只能
证明去重机会，不能充当 export 裁剪收益。用 sourcemap 估算发射字节时，不得无条件将
每行最后一条映射延伸到行尾：无映射的 JSON、运行时代码或其他模块可能被错误归给
前一个 source。将无法确认边界的尾部单列为未归因，并抽查异常大于源码的归因项。
修正归因后同步更新覆盖比例；产物整体 raw/gzip 差值独立计算。

在深入查询前，保存高影响项的选择规则、阈值及覆盖范围；按用户目标说明为何优先这些项。
将符合规则的模块全部纳入，分析其与保留原因有关的导出，不以任意 Top N 或发现一个
候选作为停止条件。其余项保留在清单中并注明优先级；新增发现的高影响项也必须入账。
缺少排序所需的产物数据时先补采；无法补齐则说明覆盖未知，不能声称已完成系统性分析。

台账保存在审计产物中，至少包含以下字段；同一快照内用 module ID 和 export path 定位，
不同版本、资源路径或 compiler 的实例不能合并：

| 字段 | 必须记录的内容 |
| --- | --- |
| 目标与优先级 | compiler/build、模块实例、导出路径、影响面和排序依据 |
| 引用调查 | 查询证据位置、已覆盖分支、待续查 frontier/offset、终点及原因 |
| 源码判定 | 消费位置、所属函数/类/回调、保留原因、编译器事实与推断 |
| 候选结论 | 待分析 / 分析中 / 确认必要 / 优化候选 / 实验无收益 / 已验证有效 / 证据不足 |
| 验证或缺口 | 拟修改位置、正确性约束、A/B 结果，或未完成原因及下一步 |

每个高影响目标继续拆成函数、类、初始化、数据表或内部依赖子树等具体实现，按
[实现保留证据规范](retention-evidence.md) 保存五环记录。不能只记录包名、`used` 数量
或“源码已解析”。一个目标可关联多条实现记录，共享证据用 ID 复用；剩余实现或分支
未分析时保持目标未完成。确认必要、实验无收益也是有效结论，但需要实际证据与排除理由。

### 2. 追完引用分支并阅读实际消费源码

按排序使用 `exports`、`references`、`chain`，再用 `reference`、`source` 阅读消费处。
列表通过 `nextOffset` 翻页；链返回 `truncated:true` 时，将每个 `frontier` 加入待办，
按 module/exportPath 继续查询，宽节点按 `nextReferenceOffset` 续查。
跨查询按快照、模块、导出路径和边身份去重，记录共享节点与循环，避免重复展开。
达到单次工具的深度/条数上限不代表分析完成。

对每个调查目标覆盖所有捕获到的上游分支，直到可解释的入口、模块级执行或已分析节点。
逐边保留消费源码片段、位置、ownerChain 和图中记录的消费方导出；共享证据可链接复用。
不能只找一条路径就概括整个导出的保留原因。例如函数被某个 class 使用时，继续查看
class 的消费和实例化位置，而非停在函数到 class 这一层。

匿名或模块级消费不能强行归属为具名导出；必要时结合模块依赖图和源码继续解释执行来源。
原生边缺失、无具名 origin、映射缺口都需要明确标注。`incomingReferences:0`、
`used:unknown` 或遍历终止本身均不是无使用证据。源码映射要核对来源和精度，保留
post-loader 文本；把 AST 归属推断与编译器确认的 export 关系分别记录。

对准备修改的目标，必须将 export usage 入边与模块依赖图交叉核对；即使原生入边非零，
也不能据此认定消费者已查全。CJS require、动态 import、拼接模块边界可能只出现在
模块依赖图中。将这些补充入口及其实际成员消费纳入同一台账，拼接父模块要继续定位
到子模块源码。组件透传 props 或包装函数转交参数时，继续追查调用方的取值范围。
不能从单个消费者固定使用某功能，推断整个应用都只需要该功能。

替换依赖的功能子集入口后，检查旧入口是否仍被其他消费者保留，并检查是否新增第二份
实现。功能测试通过不代表体积优化有效；旧版与子集版并存而增大的实验应记录为负收益。

### 3. 对每个高影响项作优化判定

结合调用上下文、原始源码、post-loader 代码、package 元数据和实际产物，逐项判断：

- 是否是业务必要使用，或可通过收窄导入、依赖对齐、调整调用位置减少保留；重复版本
  必须分析各自消费者及兼容约束，不能仅凭重复断定可以删除。
- 是否因副作用分析而保留初始化或整个模块；exports 未使用或 unknown 仅是线索，
  要检查顶层执行、注册和初始化行为，不能据此直接删除或标记为纯。
- loader 的语法降级是否使原有可分析关系丢失，例如 `await import()` 的转换。
- 上游打包器是否把 namespace 提前物化为运行时对象，例如 Rollup 的
  `Object.freeze({ __proto__: null, foo, bar })` 或 esbuild 的 export helper/getter map；
  检查实际成员读取及对象逃逸，再判断从包源码引入对应导出是否有帮助。

涉及 tree shaking 能力或误判时，核对实际使用版本的
[Rspack 源码](https://github.com/web-infra-dev/rspack/) 中 inner_graph、side effect plugin
及相关实现，记录支持结论的文件/版本。不能仅凭语法外观或其他版本的能力作判断。
每个高影响项都必须形成有证据的结论，包括“确认必要”或“证据不足”，不能只列包名。
对候选明确哪段已发射实现可能不被业务需要、什么具体操作扩大了保留，以及解除该操作
后预计消失的实现。优先调查这类保留原因；模块大、导出多和 `unused` 名称多本身不证明
可节省字节。若 Rspack 已将该实现删掉，记录“已优化”，不重复计作新空间。

### 4. 验证候选并核对覆盖情况

每个候选说明具体修改点、预计消除的保留原因和行为约束，再进行单变量生产 A/B。
只有已证明初始化无副作用时，才考虑 `@__PURE__`、`@__NO_SIDE_EFFECTS__` 或
`pure_functions` 等标记。记录同口径产物变化及相关正确性验证；源码规模估算、链变短
或模块数下降均不能替代实际 JS 体积收益。仅分析任务中保留证据并恢复实验修改。
无法安全验证的候选记录原因，不能记为有效优化。

对声称 export 裁剪的候选，补齐具体实现的产物证据：确认 before 中存在，按源码身份与
函数/数据范围核对 after 中是否消失、收缩或搬移，搜索同一统计范围的所有资产。
source map 必须先验证其文本对应原资源还是 post-loader，不能混用行号；零映射、名称
搜不到、`used` 减少均不能单独证明删除。边界不清、map 缺失或内联/共享实现时保留缺口，
按 [证据规范](retention-evidence.md#4-产物证据) 补查。函数范围的映射字节只作归因，
整项净收益由完整资产生产 A/B 给出，不能将全部差值归到一个示例函数。

结束前逐项核对影响面清单和台账：高影响项是否全部分析、引用分页与 frontier 是否处理、
每项是否有源码判定、候选是否有验证结果。报告已完成/总项数、未决分支和证据缺口，
将“工具验证”“优化分析”“收益验证”分别说明。未完成调查的项保持未完成状态，不能
通过改写为“建议”或“证据不足”掩盖未执行的查询；可修复的采集/查询问题先修复重试。
没有发现安全有效的优化可以是结论，但必须以覆盖记录和排除理由支撑。
每次形成新结论时同步实现记录与所属目标的状态、证据链接、待查分支和测量结果，交付前
核对报告与台账。候选已验证但目标仍有分支时，同时显示这两个状态；不能把目标的
`semanticAnalysisComplete` 自动设为 true，也不能让已验证候选仅存在于另一份报告而
目标仍保留过时的“尚未实验”说明。

## 语法降级造成的优化效果不佳

通过将 swc-loader 或 babel-loader 的 target 配置成最新的 ecma 版本（需要注意如果配置了 env，swc-loader 会忽略 target），然后执行一次正常的构建，构建后查看体积是否明显降低，如果降幅明显，则继续检查是否有 module 数量的降低，因为更高级别的 ecma 等级可能让某些语法不再被 bundler 视为有副作用。如果发现 module 数量有降低，则记录下所有减少的 module，然后通过上一步的 export 和源码信息分析是什么语法降级导致优化没有了。

重点检查 dynamic import：比较转换前后 `import()` 结果的消费方式，确认 namespace
成员读取是否变成编译器无法识别的普通对象访问。根据当前版本支持的语法或导出提示，
优先尝试局部源码修改；需要批量处理时，再由 agent 编写适合当前项目的 loader。
只有能确认完整使用的导出集合时才添加导出限制，namespace 作为完整对象传递或动态取值
时不能仅凭局部读取推断。对转换后的代码验证行为，并通过生产 A/B 构建确认收益。

提高 target 的实验用于定位原因。调查结束后恢复项目原本的 target，再优化调查出的
模块，并通过生产构建验证最终修改满足实际支持的运行环境。
