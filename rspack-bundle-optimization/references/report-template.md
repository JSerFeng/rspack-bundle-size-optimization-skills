# 普通用户报告模板

用 HTML 简化用户理解成本，语言保持通俗易懂，每一个优化要详细解释背后的原理，按照每一个优化项一个一个介绍背景，优化的收益，优化的方式，单位用 Kb，降低幅度要计算相比 base 的百分比。

## 落地的修改

每项修改使用相同的五行结构，保持问题与收益一一对应：

### 修改名称

- **原来的问题：** 用普通语言描述为什么多加载或多生成了代码。
- **实际修改：** 指出改动的文件和行为，不贴大段源码。
- **实际收益：** 写该项独立生产 A/B 的原始字节数、gzip，以及适用的请求结果。
- **为什么有效：** 一句话解释代码与产物变化的因果关系。
- **验证：** 列出生产构建的检查结果。

涉及 export 裁剪时，按 [实现保留证据规范](retention-evidence.md) 将以下证据连到每项
优化，正文用简短伪代码解释修改前为什么保留、修改后怎样解除：

- 具体保留的函数、数据或子树，以及有身份校验的源码范围；
- 导致保留的引用链、实际消费操作和匿名/CJS 边界的补充证据；
- 单变量修改及保留的功能、API、副作用约束；
- before/after 中该实现存在、消失、收缩或搬移的证据，缺失 map 等局限；
- 完整产物 raw/gzip A/B 和相关行为验证，未验证的行为明确说明。

图里的 `used` 数量、函数映射字节和完整资产净收益分别展示。两个示例函数消失，不代表
该项全部收益都来自它们；也不能把别处仍存在的实现写成整段删除。

## 正文语言规则

正文避免互联网行业黑话。

### 精确测量

每个统计范围的精确体积，单位 Kb、gzip 字节数和资源数量；

## Export usage 分析覆盖与未完成项

涉及系统性引用分析时，正文说明分析范围、高影响项已完成/总数、主要保留原因、找到的
候选及实测结果。附上影响面排序清单和分析台账，列明选择规则、覆盖范围、排除理由、
待续查分支和证据缺口。工具查询次数及映射测试结果单独列为工具验证，不能代替分析覆盖。

没有收益时区分“分析后确认必要”“实验无收益”和“尚未分析或验证”。仍有高影响项
未分析、引用分支未追完或关键证据缺失时，明确报告部分完成及下一步。
分别列出结构检查、目标语义分析完成、候选验证完成的数量和各自分母，报告与台账状态
保持一致。目标仍有未决实现时，允许展示该目标下某个已验证候选，但不能将整个目标
计为分析完成。已确认必要的目标说明为何没有改动，不要求为了完成记录制造优化。
